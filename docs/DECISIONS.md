# Decisions

Settled calls. Don't reopen these in code or docs without Julius approving the change. Newest at the bottom.

## The direction

- **Your game is your game.** Zaisma is simple and transparent. We provide what developers need (hosting, rooms, a database, accounts, the SDK) at their convenience, all or mostly optional, with no ifs or buts beyond misuse and hosting fees. We never take a cut of revenue: our fees are for things developers can reason about and account for, like hosting. It's why everything is open source. Every future decision follows this: give developers building blocks with full access rather than Zaisma-run features, screens or rules, and keep for Zaisma only what safety needs (Oct 13, 2026).
- **Zaisma is the player's layer; the game is the developer's.** Like Steam: nobody plays Steam, they play a game on Steam. Inside the game frame everything is the developer's, and Zaisma adds only optional building blocks and safety. Outside it, Zaisma runs what follows the player across games (account, friends, library, profile, ratings, achievements), and each piece is about playing, controlled by the developer for their own game, and open to them through the API. Zaisma never puts a platform currency, avatar or interface inside games, and runs no conversation features of its own: chat happens in games, on hosting we provide. The one exception is the developer forum, where developers and their AI talk with Zaisma and each other about Zaisma itself (Oct 14, 2026).
- **Honest clients make it smooth; the server keeps the backstop.** Zaisma's SDK and pages do extra work for the honest majority, so things feel instant: say goodbye the moment a player leaves, say "away" when the game is hidden, show a player's own view without the room they just left straight away, measure which region is closest. Nothing about safety, fairness or money depends on a client: anything a good client does, a bad one can fake or skip, so the server always keeps the slower backstop (pings, timeouts and its own checks). Every future feature follows this: design the fast path for honest clients and the backstop for everyone else (Oct 14, 2026).
- **What a developer can see, their AI can see.** Everything a developer sees or does in the dashboard, and everything Zaisma makes public, their AI reaches through the API and MCP with the same data. The dashboard is built on that API, so no screen shows what the API can't, and no feature ships on a page alone. Exceptions are deliberate and named: making API keys stays on the account page, so an AI can't hand itself new keys. The other way round is fine: the API and MCP can give an AI more than the pages show a person, like how many posts are left today, when it only matters to something working at an AI's pace (Oct 14, 2026).
- **Nothing for an AI to guess.** Every name and value in the API, MCP, SDK and game server says what it is, what kind of value it holds and in what unit, so an AI makes the right call the first time instead of working it out. Names follow one naming guide (`docs/NAMING.md`) in whole words: a duration says it's a duration and its unit (`play_duration_min`), a count says it's a count (`file_count`), a list is a plural (`files`), a point in time is an ISO date (`published_at`) and an ID says its kind (`version_…`). Each field holds one type in one unit, and one name means one thing everywhere. Inputs are closed: fixed lists instead of free text, templates instead of free-form objects, and examples, good and bad, wherever a call is easy to get wrong, as many as it takes. Outputs have a schema, errors give a stable code and how to fix it, and every change answers with the next call ready to make. The same guidance reaches every AI, not just Claude: the MCP's prompts and resources, a skill and plain docs. Fewer guesses means fewer tokens and fewer wrong calls. Until the beta opens, old names don't keep working: a clean change beats carrying two names (Oct 14, 2026). After it, "What's live keeps working" says how a name changes. It holds for Zaisma's own code too: database columns, types, functions and variables use the same names, so the inside and the outside never need translating. Agents work in the platform's code all day, and ambiguity there leaks into the names developers see (Oct 15, 2026).
- **What's live keeps working.** From the day the beta opens, a developer's game, their game server and their AI's habits keep working without them touching anything. How strict this is depends on who's there to notice a change:
  - **Inside games** (the SDK at `_zaisma/v1.js`, the game server API in Zaisma rooms, the save format and player passes): nothing in v1 ever breaks; it only gains things. A change that would break something becomes v2, served beside v1, and v1 keeps running every game built on it. A published game runs for years with nobody watching it.
  - **The developer API, MCP and upload command** (an AI or a script is on the other end): they gain things freely: tools, optional inputs, fields in answers, choice values and error codes. A renamed or retired input or tool answers with a coded error that names its replacement (`renamed_field`, `retired_tool`), so an AI fixes the call in one step. A field in an answer is never renamed, removed, or changed in type or unit without notice: the old field stays beside the new one for at least 90 days, its schema says what replaces it and when it goes, and the forum announces it. Today's paths (`/api/dev`, `/mcp`) are v1; a v2 would get paths of its own.
  - **Zaisma's own insides** (columns, code, the admin MCP): no promise; clean changes as now.

  Until the beta, clean changes stay the rule: nobody else builds on Zaisma yet, so carrying two names would only cost us (Oct 16, 2026).

## Who we serve

- **Developers first.** Players come through developers' games and shared links.
- **13+ at launch.** Age question at signup (birth date; block and don't store under-13s). We keep only the age band (13–15, 16–17 or 18+), never the birth date; accounts made before the third band are asked again before they can chat. Under-13 support later, as its own project with verified parental consent.
- **No ID, face scans or third-party age checks, ever.** We protect against real harms (contact from strangers, scams, gambling) instead of verifying who people are. Zaisma has no adult content, and its social features are built teen-safe: game communities have public posts that are checked before they appear, and who can talk to whom follows the player's age band and social mode. The protections are built for players who answer honestly; someone who lies about their age takes that risk on themselves. If a law ever demanded ID checks for a feature, we'd drop or limit that feature rather than collect IDs.
- **Making an account takes a birthday, a username and a password, nothing else.** Kids carry what's in their head to any device (a school laptop, a friend's computer), while a passkey lives on one device and an email code needs whatever holds their inbox, so neither is the way in (Julius, Oct 16, 2026). The username is public and unique: it's the player's name everywhere, and a display name comes later as a profile option shown beside @username, so nobody can pass as someone else. When a username is taken, the page suggests free ones straight away. The age question still comes first, so we never collect anything from under-13s, and "Sign in" never creates accounts, so it can't skip the question. Google and Discord stay as other ways in, and their players pick a username too. Email is no longer needed: like a passkey, it's an optional way back in. Phone numbers are never asked for. Sign-up gets Cloudflare's invisible bot check (Turnstile), never a visible puzzle: it stops mass sign-ups, and what stops a banned player coming back is that a new account starts with nothing. Supabase still checks passwords (it keeps only a hash) and issues sessions; an account without an email is known to Supabase by an address on a Zaisma domain that receives no mail. Passwords known from breaches are refused (a Have I Been Pwned range check, which never sends the password), sign-in tries are limited, and there are no complexity rules. The username, age band and social mode live in our own database next to the games. Deleting an account is instant.
- **Accounts get protected once there's something to lose.** A fresh account has nothing worth stealing, so sign-up asks for nothing more. Once a player comes back to progress they've saved, Zaisma's own pages (never over a game) show once: "Protect your account. Add a passkey or an email so only you can sign in, even if someone learns your password." with Add a passkey, Add an email and Later; after that it stays as a line on the account page. The words stay plain (never "vulnerable" or "hacked", which is what phishing says), and it never asks for the password. A passkey or an email is required before anything with real value, like saving a card or linking a parent. A forgotten password comes back through the passkey or the email; an account with neither and a forgotten password is lost (Julius, Oct 16, 2026).
- **Cloud saves copy the game's own browser saves, no code needed.** For signed-in players, the game page fetches the account's save and puts it in the game's storage before the game starts, then stores the save as it changes (every 30 seconds and when the player leaves). The game never sees the account. Every save names the version it started from, so a second device never silently overwrites newer progress: when two devices differ, the progress played most recently wins and the other is kept as an earlier version (Julius, Oct 16, 2026). Saves are stored in R2, not Supabase, up to 5 MB per game per player, and deleted with the account. It covers localStorage and IndexedDB, so Unity, Godot and localForage saves work too; download caches (like Unity's) are skipped. Games with their own saves can turn it off. Up to 5 earlier versions are kept per game (one an hour while playing, plus one whenever progress is about to be replaced), as a backstop for the developer, never a rollback for players: whether a player can go back is the game's rule (Julius, Oct 16, 2026). Guests' progress stays in their browser and is never sent anywhere; once a guest has progress and has played 5 minutes, a card offers to keep it with an account (at most every 3 days after Not now), made in a new tab so the game isn't interrupted; a game setting turns the card off (Julius, Oct 16, 2026).
- **Passkeys are checked by us, sessions still come from Supabase.** Supabase's own passkeys are experimental, so the site checks passkeys itself (WebCrypto, no libraries) and asks Supabase for a one-time sign-in link it uses straight away. Adding a passkey needs a sign-in (password, email code or passkey) in the last 10 minutes, so a stolen session can't add a way back in. Passkeys are optional: offered once the account has something to lose, and a way back in when the password is forgotten.
- **Google and Discord sign-in go through Supabase, and the age question still comes first.** Someone new who comes back from Google or Discord without having answered it is deleted from Supabase straight away and asked it before continuing, so we keep nothing from under-13s. Existing accounts with the same email just sign in.
- **Guests play with no account.** A temporary guest ID used only to run the session: no chat, no purchases, no profile, no personal data. The age gate appears when a guest makes an account.
- **Players can mute, block and report other players**, so one person can't ruin a match or follow someone between games. A mute lasts for the room. A block follows the account (or the session, for guests) into every game, and it's a brick wall both ways: nothing either one sends reaches the other (messages, emotes, voice, friend requests, invites), neither shows up in the other's friends, profile or where friends are playing, and Zaisma never helps either one find the other (join a friend, finding players across rooms). Blocking a friend ends the friendship, and the blocked player isn't told. A block never keeps anyone out of a room: who plays stays the game's call, and one player's preference is never enforced on another. It's the blocker's own preference instead, like choosing not to walk into a room rather than having someone removed from it: when Zaisma picks a room for a player (`quickJoin`), it prefers rooms without anyone they've blocked, and puts them in one only when nothing else fits, with the wall still up. The game learns when two players in its room have a block between them (never anyone's block list), so its own matchmaking can do the same. A player's blocks are listed on their friends page, each with Unblock (Julius, Oct 16, 2026).
- **Guests get generated names** like "Swift Fox 42". Player-typed names come with accounts.
- **Social modes decide who can talk to whom.** Only accounts can chat (text or voice); guests get the game's preset phrases and emotes. Every account has a social mode, changeable any time:
  - *Solo-focused:* no chat at all.
  - *Friends-focused:* text and voice chat with friends only. Friends are added by invitation (a link or code one friend gives the other), never by a stranger pressing "Add friend".
  - *Open and social:* chat with anyone in the same group, and friend requests from anyone.

  By age band: 13–15 accounts start in solo-focused and can switch only to friends-focused, by hand. 16–17 and 18+ choose a mode at signup, with friends-focused picked by default. Open and social at 16–17 reaches only other 16–17 accounts in open and social; at 18+, only 18+ accounts. Zaisma enforces this on every message: rooms deliver each message only to the players allowed to receive it, so in a mixed room a message may reach only some players. Games never learn ages: the player pass carries an opaque chat group and the player's friends, and developers' own servers ask `canChat(a, b)`. Mute, block and report work on chat everywhere (Oct 14, 2026).
- **Chat is the game's; Zaisma hosts it and keeps the safety floor.** Zaisma runs no chat of its own and draws no chat box. A game that wants chat builds its own interface and rules on Zaisma's chat hosting (text through its room, voice through Cloudflare's media server, so players never see each other's addresses) and moderates it with its own tools and moderators. Zaisma's part is the floor: social modes, the filter on every message to or from an under-18 account (`Zaisma.filterText` or an equal filter of the game's own), mute, block and report, and acting on reports, including the reports the law requires (child safety to NCMEC). Zaisma stores no chat. A chat report attaches the last messages from the reporter's own screen, and a voice report the last 30 seconds of audio the reporter's browser heard, sent only if they report. Names players give to things in a game (sessions, worlds, maps) are allowed, and the game keeps them within the content rules (Oct 14, 2026).
- **The text filter catches what matters and leaves the rest alone.** Contact details in any disguise (numbers written as words, spaced-out emails, handles, "add me on…"), slurs and sexual content aimed at teens; never scores, coordinates, item names or ordinary words. Rules run first, in the browser; only unclear messages go to a small AI model. A blocked message is not sent and the sender sees why ("contact details aren't allowed"), instead of a wall of hashes. Always on for under-18 accounts; between adults, the game's choice (Oct 14, 2026).
- **Teen-safe defaults.** 13–15: solo-focused, friends by invitation only, private profiles. 16–17: friends-focused unless they choose otherwise, private profiles. No default spending cap: spending is between a teen and whoever owns the card, and parents already have bank and phone family controls.
- **How social modes reach games.** An account's player pass carries its `social_mode` and, when open and social, a `chat_group`: a keyed hash of the game and the band group, so it matches within a group, differs in every game and never says an age. `canChat(first, second)` in `@zaisma/game-server` answers from two checked passes (friends too, below), and Zaisma rooms use it with Text chat in rooms. A change reaches a game with the player's next pass. Accounts from before the third band (13–17) became 13–15 with no chat, the strictest, until they give their birth date again; there were none outside testing (Oct 16, 2026).
- **How friends work.** Two accounts become friends when one accepts an invite the other made on zaisma.com/friends: a link (`/friends/add/<code>`) or its 8-character code, for one friend, working once for 7 days, with up to 10 waiting at a time. The invite's page names who it's from and asks before adding, and nothing else adds a friend. Friends are two-way, up to 200 each (so a pass that lists them stays small); either side removing the other ends it for both, and friends and invites go with the account. An account's passes carry its friends' player IDs (`friend_player_ids`), and `canChat` lets two accounts chat when each one's pass lists the other and neither is solo-focused, so a removal holds from either side's next pass. What friends are playing, `Zaisma.friends` and friend requests for open-and-social accounts come next, each its own item (Oct 16, 2026). The invite page stays one card with one question and one button; /friends becomes the place to manage friends (invites, the full list, blocks) once friends show on home, and both get full Steel with Account pages rather than a restyle of their own (Julius, Oct 16, 2026).

## Money

- **No cut of game revenue.** Listing is free. Selling is free.
- **Developer's choice of payments.** Our checkout is an optional free convenience. Developers can use their own Stripe, Bitcoin or anything else. The platform never holds player money.
- **One Zaisma buy sheet; we own the buying experience, not the money.** A game calls `Zaisma.buy(item)` and our page shows the same sheet over every game: item, real price, buy. Apple Pay and Google Pay, plus a card saved once on the player's Zaisma account and usable in every game (Stripe clones it to each developer's account at purchase). Developers are the sellers through Stripe Connect Standard, so sales tax, refunds and chargebacks are theirs; Stripe Tax is offered (about 0.5%), or a seller-for-you service like Paddle through their own link. Owned items are stored with the player's account, so they work on every device; games check `Zaisma.owns(item)` and game servers check signed receipts like player passes. Purchase history and receipts live in the account, and the card owner always gets a receipt. Developers can also grant items through the MCP or an API (for example, Patreon supporters). No Zaisma wallet or currency for players, and we're never the seller. (Developers' hosting credit is a separate thing: it pays only for Zaisma services; see hosting.) Card fees make tiny purchases expensive (about 30¢ each), so developers are nudged toward items of $2–3 or more.
- **Bitcoin in the buy sheet, optional.** Developers can switch on "Pay with Bitcoin" per game: Lightning for everyday purchases (fees a fraction of a cent, so small items work), on-chain for large ones. Bitcoin only; no other coins or tokens. We never hold it: each developer connects their own wallet (Nostr Wallet Connect, a Lightning Address or their own BTCPay Server), the sheet gets an invoice from it, the player pays the developer directly, and we only confirm payment before issuing the receipt. Prices show in dollars plus the sats amount, and invoices expire after a few minutes. Same receipt, owned items and history as card purchases. No chargebacks; refunds are sent by the developer under their stated policy. Never the default. Games can never ask for seed phrases or permission to spend from a player's wallet, and never pay players sats; wallets for other coins are held like scams (Julius, Oct 16, 2026).
- **More ways to pay.** The buy sheet turns on the extra payment methods Stripe supports where available (PayPal in some countries, Pix, iDEAL and other local methods). Subscriptions come later.
- **Purchases reach every kind of game.**
  - *Own game servers:* the signed player pass lists what the player owns in that game, so any server sees it on connect without calling us; a purchase or refund issues a fresh pass. We also send the developer's server a signed notification for every purchase and refund, as the permanent record.
  - *Live, mid-match purchases:* `buy()` returns a signed receipt at once; our rooms call the game server's `onPurchase`, and self-hosted servers check the receipt the game sends over its connection. Each receipt has a unique ID and counts exactly once, so consumables can't be replayed. Purchases interrupted by a disconnect are delivered on the next join. The game gets a `sheet open` event so it can pause or protect the player, a declined payment changes nothing, and refunds trigger `onRefund` (taking back spent consumables is the developer's stated policy).
  - *Games with no accounts:* the buyer signs in to Zaisma at Buy (guests can't buy); the game itself only sees `owns(item)`.
  - *Games with their own accounts:* they can offer "Sign in with Zaisma" as a login option, so their accounts and ours link up. The game passes its own player ID with the purchase, and it comes back in the receipt and notification so their server credits the right account. Or they use their own payments entirely through a registered link. Inside a game on Zaisma, no game asks players for personal details (emails, real names, birthdays, location): the game's own accounts key on the Zaisma player ID, and linking to an account elsewhere, or anything more, happens on the developer's own site (Julius, Oct 16, 2026).
  - *Own payments:* Zaisma's protections (receipts, purchase history, family controls) don't apply, so the game page says "Purchases handled by the developer, not Zaisma."
- **Hosting is priced with a margin, with a free tier, and prepaid above it.** Multiplayer on our rooms costs about twice what Cloudflare charges us (roughly $2 per 1,000 player-hours). Every developer or team gets the first 1,000 player-hours a month free, with no card and no prepayment, so family games and prototypes never pay. Above that, hosting is prepaid: the developer adds credit first (about $10 minimum, optional automatic top-up) and usage comes out of it, so everything we serve is already paid for. When credit runs out, matches already running finish, but no new rooms open beyond the free tier until they top up; never cut off mid-match. Warned at 20% left and when it runs out, by email and in the dashboard and MCP. Credit is only for Zaisma services (hosting, later Pro), is never paid out and never touches player purchases. Developers see their game server's errors, stopped loops and CPU per player-hour, so they can cut their own costs. Running your own servers is always free. Text chat rides the room's own connection and is included. Voice chat is off by default; switching it on shows a caution with the estimated cost, and a player-hour with voice counts as 2 toward the free tier and the bill (voice costs us about what a room does: $0.05 per GB sent, roughly $1–3 per 1,000 player-hours with only the loudest few speakers heard). Set before the beta, so no developer ever sees an "at cost" promise taken back. (Prepaid above the free tier approved Oct 13, 2026.)
- **Bring your own servers, any time.** Our rooms are a default, never a requirement. Moving off them is a config change, not a rewrite.
- **No ads in games, at least through beta.** Ad scripts change after we scan them, track teens and are the main source of scams on web game sites, and ad-funded design drifts toward clickbait. Developers earn through purchases, our free checkout, and tips. Promoted games are our own labeled listings, not ad networks.
- **Every game opens free.** Nothing charges before you play, so "tap a link and you're playing" always holds (at most a free Zaisma account, when the developer asks for one). Developers can still sell anything inside the game, including a full-game unlock, through the buy sheet or their own payments.
- **Honest purchase labels.** Every game page says in plain words what a game sells: "No in-game purchases" or "In-game purchases: cosmetic items".
- **No paid random rewards (loot boxes) for anyone.** Players always know what they're buying. Simpler than age checks, fits the no-slop stance, and avoids the countries that restrict them.
- **Real-money prices always shown.** If a game has its own coins or gems, the real cost appears next to them.
- **Every game that sells something states its refund policy.** The developer is the seller, so refunds and chargebacks are theirs.
- **Family controls are opt-in, never forced.** A teen can link a parent's adult Zaisma account by invite. "Ask a parent to buy" sends the parent a request to approve and pay with their own card, which is also how teens without a card can buy. Linked parents can set a spending limit and see purchase history. Nothing is checked or required.
- **Money ships right after the beta (Phase 2).** Multiplayer billing starts only from the month payments go live, so nobody pays for servers before they can earn. Until then each game's rooms stop at the free tier (1,000 player-hours a month): running matches finish and no new rooms open until the month resets, so bots and runaway games can't run up our bill.
- **Games open outside links only through Zaisma.** The sandbox blocks games from opening pages themselves. A game asks the SDK to open a link, and our page opens it in a new tab with a short "You're leaving Zaisma" notice. Only links the developer registered for that game work (their store, Patreon, Bitcoin page, Steam, Discord), so games can't send players to random sites. This is how developers' own payment methods work from inside a game.
- **Profit from services, never from a cut of sales.** Zaisma is run for profit. We make games available and developers make the games, so their sales are theirs: no cut and no listing fee, ever. We earn from services, each with a free path: hosting (above), Zaisma Pro for developers (about $10/month, only for things that cost us more: custom domains on our hosting, more storage and seats, a higher daily upload limit; a developer's own data, like stats, and features that cost nothing, like scheduled releases, are never paywalled), promoted games (labeled front-page slots, no tracking, priced by traffic) and later Zaisma Plus for players (about $5/month: badge, profile extras, new features first, early access to games whose developers opt in; half goes to developers by playtime). Donations are a bonus, not the plan. Saves, accounts, publishing and playing are never paywalled.
- **Games hosted elsewhere can be listed as link-outs.** Free, clearly marked "Plays on example.com", opening on that site, never embedded in Zaisma, so nothing unscanned runs inside it. Checked against the content rules when submitted and re-checked automatically. We list someone else's game only after they say yes, credited to them with a link to their profile and in their own words; they can claim, edit or remove it. Once developer accounts exist, developers add their own link-outs from the dashboard or MCP. Never games built on someone else's franchise (a Call of Duty zombies remake, say): the content rules apply to listings too.

Code is public; keys, player data and game files never go in the repo (secrets live in Cloudflare and Supabase settings, data in the database and storage). The PhotoDNA connector is public too, unless what Microsoft provides after approval turns out to be confidential under its license; check the moment we're approved. ## Safety and moderation

- **Scan before publish.** Malware scan, known-illegal-image matching, AI review. Every upload is scanned within minutes; the developer then publishes when ready.
- **The content rules draw exact lines, so developers don't hedge.** zaisma.com/legal/content-rules is the floor every game is held to, and each rule says where its line is, so an edgy game never has to guess. There's no hate-speech rule: offensive and edgy games are welcome. Real people are fair game for mocking, memes, satire and gameplay violence, name and photo included; what's out is anything that lets players find or reach a real person who didn't make it public (a home address, phone number, personal email or private account, where they go to school or work) and real threats of violence. Places famous on their own (the White House, Epstein's island) and accounts people publish themselves are fine. The test: could a player use it to find, call or message someone who didn't put that out there? A private person a game falsely accuses of a crime can send a notice, and we take it down as we would for copyright; we don't judge defamation ourselves. Crypto is Bitcoin only: other coins, tokens, NFTs and airdrops are held like scams (a story that mentions one is fine), while Bitcoin games are welcome (teaching it, themes, selling items for sats through the buy sheet, tips), but never investment advice, mining on the player's device, paying players sats, or asking for seed phrases or permission to spend from a wallet. Sats go from players to developers, never from a game to players: honest earn-sats games are funded by ads, which Zaisma games don't have, so what's left is the deposit-and-referral kind. Breaking a rule costs a version, never more by surprise: the version is held or the live game hidden, with the rule, what we found and the fix, nothing is deleted, and a fixed version brings it back. Accounts are closed only for sexual content involving minors, malware, or putting back something we already took down. When a country's law forbids what US law allows (the UK's hatred offences, say), a notice from there blocks the game for players in that country, never everywhere (Julius, Oct 16, 2026).
- **Zaisma steps into players' chat only where block can't help.** How players talk to each other, fiery lobbies and trash talk included, is up to each game and its moderators, with mute and block always there. Zaisma acts on four things: real threats, sharing someone's personal details, following someone after they've blocked you, and anything sexual toward a teen. Other chat reports tell the player to mute or block and go to the game's moderators, and cheating reports go to the developer, since it's their rule. Teens keep their age bands, the always-on filter and block (Julius, Oct 16, 2026).
- **Known abuse material comes off at once.** Image matching (Arachnid Shield) checks every picture and video in an upload, whatever it's named or hidden in, and every cover and screenshot. A match isn't a report or an AI opinion, so the rules that keep established games up don't apply: the version is held and can't be approved, a live game is hidden until the developer publishes a clean version, nothing is deleted, the developer is told only that a person needs to look, and Julius gets an urgent alert to report it to NCMEC. Versions that passed before matching was connected are matched once, by a daily job.
- **Two lists, either one holds.** PhotoDNA (Microsoft) checks every still picture alongside Arachnid Shield; videos stay with Arachnid Shield, and an animated GIF's first frame goes to both. A match on either list holds the version, and the alert names which list matched. A version waits for a person only when both services fail; if only PhotoDNA fails or is rate-limited, the version passes on Arachnid Shield's check and PhotoDNA matches it later, like the daily job. Microsoft allows 5 requests a second (5 pictures each) and 10 million a month, so every check goes through one shared pacer, new uploads before rechecks. PhotoDNA's license keeps AI agents away from its SDK's libraries (`*.dll`, `*.so.*`, `*.nupkg`, `*.wasm`, `photoDnaEdgeHashS.js`) and needs AI training turned off; agents work from its wrappers, samples and `PhotoDnaEdgeHashGenerator.md`. The SDK never enters the public repo: it lives in `~/zaisma-private/photodna-sdk/` and is added only when Julius's machine deploys, and builds without it simply run without PhotoDNA. *(Julius, Oct 16, 2026)*
- **A match in player content takes down only that item.** When Zaisma stores something players made (community posts, pictures in cloud saves), image matching checks it too, and a match removes that one item and keeps it for reporting, never the game it's in. The account that uploaded it is dealt with, not the developer. Image matching never looks at player content kept on a developer's own servers; that's theirs to check.
- **Scan only what changed.** Files are fingerprinted, and an update reuses earlier results for unchanged files. Updates are limited per game per day (about 20) so a broken script can't upload in a loop.
- **Moderation pays for itself.** A capped free review budget per developer (not per game), then refundable $5 / $25 deposits, so floods from bad actors cost them, not us.
- **Games are sandboxed** on a separate game domain, never on zaisma.com.
- **Report button on every game page**, DMCA agent registered, takedown on notice.
- **Game domain: zaismausercontent.com**, one subdomain per game (`<slug>.zaismausercontent.com`), so games can't read each other's storage. Named like googleusercontent.com: it says "made by someone else", which makes official-looking phishing subdomains harder, and a plain .com is cheap, rarely blocked by school filters and free of country-domain politics. Players rarely see it: shared links stay `zaisma.com/g/<slug>`. The bare domain redirects to zaisma.com and never serves games, and slugs that could pass for official pages (login, support, billing and so on) are reserved. We apply to the Public Suffix List so browsers treat each game as its own site (separate cookies, and a phishing flag on one game doesn't block the rest); the list wants at least two years left on the registration. zaisma.gg is optional, only ever as a vanity redirect.
- **Games can't load outside scripts, and connect only to Zaisma rooms and their own servers.** Every file we host is scanned, so developers bundle their libraries; a game's own servers send it data (moves, levels, scores), never code to run, and the scan flags games that download code and run it. A game may connect to `rooms.zaisma.com` and to its own servers: up to 5 addresses, set by the developer from the dashboard, API, MCP or upload command, live at once with no approval by Zaisma, recorded in the game's history and named on the game page in plain words ("Also uses the developer's own server: play.example.com"); games that only use Zaisma rooms show nothing; nothing else. What we promise is what we can check: the files we host are scanned, the page names any outside servers, and everything a game shows players, wherever it comes from, is under the content rules and can be reported. A person approving an address would see only a name, never what the server sends (Julius, Oct 16, 2026).
- **Uploads are only for people Julius adds until the beta.** Any account can sign in, play, keep saves and add friends, but until the beta only Julius, Gleb and accounts Julius adds can make games, from the dashboard, the API, the MCP or the upload command. Everyone else sees "Publishing opens with the beta" in Your games, and the API answers the same as a structured error. The DMCA agent and NCMEC reporting must be in place before strangers' uploads land on the LLC. Uploads open to every account when the beta opens (Julius, Oct 16, 2026).
- **We only list games we host.** Every listed game's files are served by Zaisma, because we promise that every file we host is scanned. Self-hosting means the multiplayer game server, never the game files. (Clearly marked outbound links to games hosted elsewhere could come after beta if developers ask.)
- **The game page shows details first, then plays.** `zaisma.com/g/<game>` opens on the game's details (cover, title, description, multiplayer and later screenshots, device labels and the developer's links) with one big **Play** button; tapping it turns the page into the game, with no reload. The game only loads on Play, and that tap also lets it play sound straight away. Room links (`?room=CODE`) skip the details and drop the player into the match.
- **Nothing of ours constantly on top of the game.** While playing, the game page has a slim bar beside the game: Z (home), the title, Share, Full screen and a ⋯ menu (about the game, its own servers, Report, content rules). On phones the bar uses icons, and in landscape it becomes a strip down the left edge so the game keeps its full height. Menus the player opens may cover the game; nothing of ours sits over it by default, and in full screen the game has the whole screen. No floating logo, no watermark: the test for anything we put in front of a developer's game is whether it serves players, not whether it advertises us. No "more games" while someone is playing; recommendations come with discovery, between games. Embeds and custom domains get a small link to Zaisma beside or below the game, never over it.
- **Invites belong in the game.** The game knows when to invite ("waiting for players"), so the SDK gives it `Zaisma.invite(room)`: the share sheet on phones, a copied room link elsewhere. Our Share button shares the address bar, which carries the room code during a match.
- **Support, reports and moderation are designed for AI first.** People only make judgment calls. Every hold, takedown, bill and failed upload records a plain reason, the rule and how to fix it, with an error code that links to docs, so the answer to "why?" always exists as data. Holds and takedowns name it as a `review_reason`: a code from one list (`REVIEW_CODES`, listed in docs/DEVELOPER-API.md), a plain message, the content rule it's about and the fix. A person who takes a game down picks the rule it broke and writes the why the developer reads, except for child safety, which is never described (Oct 16, 2026). Developers' own AI answers their questions through the MCP; everyone else gets an AI assistant on zaisma.com that reads the same records, answers from facts and takes safe actions (resend a code, re-run a scan). Every report is triaged by AI: sorted by severity, duplicates merged, evidence gathered, safe outcomes handled (re-check the game, tell the developer about a bug, hold a clear rule break). Bans, takedowns, appeals and disputes reach a person as a summary with a recommendation, decided in one click. Child-safety reports always go to a person first; AI only puts them at the top of the queue. Recurring questions become product fixes, not canned replies.
- **Games where players interact offer mute, block and report in their own menu.** That's how a player reports someone mid-match without leaving the game. The SDK provides a ready-made panel in one line that the game can style; on Zaisma its Report hands over to Zaisma's own report plate, so every report looks the same and carries the room and the player's temporary ID.
- **Reporting never leaves the game.** Report opens a plate beside the game (up from the bottom on phones) while the game keeps running: tap what's wrong, add details if you like, send. It includes the version being played and the room, never anything about the person reporting. Every game can be reported, whatever its visibility.
- **No single report takes an established game offline.** Child-safety and illegal-content reports always go straight to a person, marked urgent. Until a person looks: a brand-new game (its only version went live in the last 7 days) is hidden, and an update from the last 7 days goes back to the version before it while the update is held. A version a person cleared, or one a report already went back to, is never paused by reports again, so a griefer gets at most one pause per version. Anything else stays up. The developer sees "a report paused your game/update while we check it", never which kind of report.
- **Report triage acts on evidence in the game's files, never on a report's words alone.** Within minutes, AI sorts every report by severity (child-safety ones without any AI reading them), merges reports about the same problem, passes bugs to the developer, and can have the live version's files checked again, once per version. Only something new that check finds counts, and then under the same rule as reports: a brand-new game is hidden and a recent update goes back a version until a person decides; an established game stays up for a person to decide, since its files haven't changed since its scan and a second AI opinion on them isn't enough. However many reports come in, they're one card and one re-check per version; volume never takes a game down. Everything else waits in the report queue with a summary and a recommendation, decided in one click. If the AI finds child safety in a report sent for another reason, it's treated as a child-safety report. Child-safety and illegal-content reports are alerted the moment they arrive; others once sorted, if urgent or high. When the AI budget runs out, reports are sorted by their reason and all alerted.
- **Moderation follows precedents.** A precedent is a short ruling a person made: what the case looks like, the decision and why. Triage says which precedent a report fits, that none does, or that the report challenges one. A case that fits is decided the same way, and a dismissal precedent a person marked for the AI alone is applied without a person, except 1 in 20 kept as a spot-check. New cases and challenges reach a person with a drafted ruling, and deciding them sets or changes the precedent in the same click. Changing a precedent makes a new one, so past decisions keep the wording they followed. Limits: child safety is never automatic, takedowns always need a person, and a re-check pauses a game only over a problem the code finds in its files (a rule-based check, or an exact quote from the AI that really is in the file).
- **Reports can include a picture of the game.** Taken from the game's canvas when the player opens the menu or Report, shown in the plate, and sent only if they keep it ticked. Never with child-safety or illegal-content reports (the reported version is kept instead). Only admins and the AI triage see pictures; they're deleted 30 days after the report closes. Players never upload their own images.
- **Same rules at every visibility.** Draft, unlisted and private games are scanned, reportable and bound by the content rules exactly like listed ones.

## Discovery

- **Progress bar to the front page.** Games earn front-page placement by clearing a visible bar built on quality: how many players come back, how long they play, ratings from people who actually played, and reports. Raw play counts never decide placement on their own, and there's no "Most played" shelf.
- **"New and rising" shelf** so new games get seen before they clear the bar, with a quality bar of its own.
- **No slop.** Zaisma never looks like a wall of clickbait. Cover images and titles can't use fake rewards or currency bait ("Free Robux"), famous characters or brands the developer doesn't own, or art that doesn't show the actual game; the AI review checks covers. Fake rewards and brands the developer doesn't own hold the game (scams and other people's property); other slop only keeps it off the shelves until the cover is fixed. Every game page shows real screenshots or gameplay next to the cover. No swipe feed: it amplifies clickbait.
- **Discovery through people.** Player-made lists, developer picks, game jam winners and "New and rising", plus search by genre and tags.
- **Ratings only from people who played** for a few minutes, so there are no drive-by or fake reviews. Developers can reply to ratings, and their games' ratings are theirs to read through the API.
- **Copycats made visible.** Remixes show what they're based on, and the same template reposted with new skins counts as one game for discovery.

## Product scope

- **Browser only; no native desktop downloads.** Native downloads contradict "no app download", would make us a malware distributor the first time a scan misses something, and need code signing and per-OS builds. Instead every game gets an **Install** button: an installable web app (PWA) with its own icon, window and offline play, in the same sandbox. Developers with native builds link to their Steam or itch.io page from their game page.
- **Fit any game; never make developers rebuild for Zaisma.** Integration comes in optional layers, and a game can stop at any of them:
  - *Layer 0, no changes:* any web game that runs from an `index.html` uploads as is (Phaser, Three.js, Unity and Godot web exports, single-file AI games), with its own saves working. The upload command fixes common blockers itself: it downloads scripts loaded from outside sites into the game (so they're scanned) and unpacks pre-compressed engine builds. `zaisma check` (also an MCP tool) lists anything else that won't work and how to fix it.
  - *Layer 1, one script tag:* cloud saves that mirror the game's own browser saves for signed-in players, and the right name and invite link on the game page, with no code.
  - *Layer 2, a few calls:* rooms, invite links and player names. Drop-in replacements for Socket.IO and PeerJS route existing multiplayer prototypes through our rooms with little code change.
  - *Layer 3, built around Zaisma:* game servers, accounts, friends, purchases, mods.

  No required engine, framework, avatar or world; the SDK is small plain JavaScript. We provide data and the game draws its own screens (ready-made screens are optional). The skill and MCP do the adapting. Nothing locks developers in: passes are standard signed tokens, game servers are plain JavaScript over WebSockets, and off Zaisma the SDK points at the developer's own server or falls back to solo. The fixed limits, stated upfront: the sandbox, no ads, no free-text chat for guests, and mute, block and report in multiplayer games.
- **Custom game domains with Zaisma Pro (Phase 2).** Developers can point their own domain at their game (Cloudflare for SaaS: first 100 domains free, then about $0.10 each a month). Same scanning, sandbox and takedown rules.
- **Multiplayer rooms use WebSocket hibernation from day one** (Cloudflare Durable Objects). Without it, costs are 10x+.
- **Multiplayer is server-client by default.** The game server holds the official state and checks every move; a messages-only relay is there for simple games. While only Julius uploads, game servers are built into our rooms Worker. Once outside developers upload, they run in Cloudflare Dynamic Workers (needs Workers Paid, $5/month).
- **Call it the Zaisma SDK.** The small JavaScript library games include (`zaisma.js`) plus the game server package. Developers search for "SDK", so use that in code, docs and copy, not "toolkit". Services are grouped: `Zaisma.player`, `.rooms`, `.saves`, `.store`, `.achievements`, `.friends`, `.chat`, `.links`, `.demo`; every part optional (leaderboards live in the game's own database), with a plain web API underneath for other engines.
- **Multiplayer words: client, game server, room.** The *client* is the game in the player's browser. The *game server* is the developer's server-side code that holds the official game state. A *room* is one live match, running one copy of the game server. Use these game-dev terms in code, docs and copy (not "room script" or "backend").
- **Developer MCP first.** Developers manage everything from any AI tool through our MCP server, with a small upload command for builds (too big for MCP calls) and a skill on top that every AI can use, not only Claude (Oct 14, 2026). The website dashboard and the MCP use the same API, so they always agree. Deleting or unpublishing a game needs confirmation.
- **The dashboard is three kinds of page.** The *developer home* (zaisma.com/dashboard) shows your games as cards with their status and alerts. *Developer settings*, a page of its own linked from home, holds what applies across all games: webhooks and sign-in apps as simple lists, a link to API keys (which stay on the account page), and later hosting credit and teams. *Each game's dashboard* is split into sections, each with a fixed layout: Overview, Versions (with tester links), Details (with images), Players and stats, Database, and Updates and Achievements when they land; the title and who can play sit on every section. Each developer can reorder, hide and show a game's sections, per game and per person, since an MMO and a platformer need different things; new games show every section, and an unused one says what it's for. Overview always comes first and can't be hidden, and it shows everything urgent (a held version, a takedown, open reports, rooms or requests paused) whatever else is hidden. Customizing inside a section can come later. Saves stay in the API, MCP and upload command only: a save is one player's raw data, better handled by an AI that knows the game than by a form (Julius, Oct 16, 2026).
- **Uploads are drafts.** Each upload is a version. Once it passes the scan, the developer gets a private preview link; nothing unscanned is shown to anyone. Details (name, description, cover, screenshots) are drafted and scanned too. The developer publishes now or schedules it, and can roll back to any kept version in one click. We keep the live version plus the last 5 approved; unpublished drafts are deleted after 30 days. Code history belongs in the developer's own Git.
- **Developers own many games; visibility and review are separate.** Visibility is the developer's: draft, listed (directory and search), unlisted (anyone with the link) or private (only through tester links). Unlisted games never appear in the directory, search, "More games", our sitemap or search engines (`noindex`). Private games open only through secret tester links the developer makes, names and can revoke at any time, one per group (team, playtesters, a streamer); testers can play as guests, and after accounts developers can also invite specific accounts. Review status is ours: live, under review or removed. Changing visibility never undoes a takedown. Teams come after beta (see below), but from the beta every game is owned by an owner that can later be a person or a team, so teams drop in without rebuilding the database.
- **Big games are welcome.** From the beta the upload command sends files one by one straight to storage (no zip through a Worker), stored by fingerprint so versions share unchanged files and updates only upload what changed. Limits: 2 GB per game (more on request), 500 MB per file, 20,000 files. Until then the current limits stay (25 MB zip, 100 MB unpacked). The SDK and skill teach loading in pieces so big games start fast, and the game page shows the download size and warns phone players before big downloads.
- **Device labels.** Developers state devices (phone, tablet, computer), controls (touch, keyboard and mouse, gamepad) and screen (portrait, landscape, either). Games for the player's device come first; others show a note and "Play anyway", never a block. The game page shows devices as icons; controls and screen only come up when they matter, as a note on a device that doesn't fit ("Best in landscape", "Needs a keyboard").
- **Developer play stats built in.** Plays, session length and retention in the dashboard and MCP, so games don't need outside analytics (which the sandbox blocks anyway). The daily counts are the developer's to export through the API, and games can count their own events (`Zaisma.track`, no player IDs) next to them.
- **Counted plays are the official numbers.** A play counts once Cloudflare's invisible check (Turnstile) says a real browser pressed Play and the game has been on screen for a minute (the check starts when the game page opens, so Play doesn't wait for it; Julius approved Oct 14, 2026); each check works once, and a play's time can't be claimed faster than it passes. Developers see counted plays first, with every play started as a smaller line; Popular and Trending use only counted players, without cloud and hosting networks, and with no single internet provider carrying more than 30% of a game's players. Players are counted by internet provider (ASN), only as totals, never by address. The developer's own plays and tester links don't count. The check never blocks or slows playing alone: a play it can't check still runs, it just isn't counted. Admin sees spikes (5 times the week before) with how spread out they are, and can remove a day's counts or keep a game off the shelves. Faking plays breaks the content rules: off Popular, Trending and New, then takedown for doing it again. Later: payouts by playtime (Zaisma Plus) only from signed-in accounts.
- **Multiplayer needs the check on Play.** A Zaisma player pass (for our rooms or a game's own servers) is given only to a browser the same check let in: the game page gets a key, hands it to its own game, and each key gives up to 5 passes over 6 hours. So bots can't fill rooms or fake "playing now", which counts only players with passes. The developer's own plays and tester links get keys too (still never counted). A player the check can't confirm after Cloudflare's checkbox plays alone but not online, and a game opened outside its zaisma.com page gets no passes. (Julius approved the strict version Oct 13, 2026.)
- **Play inside Discord, after beta.** Our rooms work through Discord's proxy, so developers can ship their own Discord Activity for their game; on top of that, one "Zaisma" Discord Activity opens any game, and everyone in the call lands in the same room, using Discord's voice. Games stay hosted, scanned and sandboxed by us; Discord just shows our page. Players can choose to share their Discord name, otherwise they play as guests. Needs Discord's app review and our rooms set up for Discord's proxy.
- **Bigger game servers, after beta.** For games that outgrow rooms (more players, heavy physics, Godot or Unity server builds): Cloudflare Containers, each sealed in its own virtual machine, priced like rooms, with a margin over what it costs us (about $3 per 1,000 player-hours at cost for a 1-core server shared by 32 players; check outbound data charges first). Developers' own servers stay free for us and allowed from the beta.
- **Remixes, soon after beta.** Developers can switch on "Allow remixes" (off by default). A **Remix** button (also an MCP tool) copies the game into a new draft for the remixer. The credit line "Based on <game> by <developer>" is automatic and can't be removed, and the game page shows the remix chain. Remixes share the original's stored files and only changed files are scanned, so a remix starts almost free. Remixing a game that doesn't allow it is handled as a copyright issue. Developers can also choose "If I stop updating this game for 12 months, allow remixes", so the community can keep abandoned games alive; credit still goes to them.
- **Teams, after beta.** A team owns games instead of a person, like GitHub organizations or Roblox groups. Roles: owner (members, payouts, transfer or delete games), publisher (publish, schedule, roll back) and developer (upload drafts, preview links). Games move between a person and a team without losing their link, players or history. The MCP acts as the member with their role, and the audit log records who did what. Review budgets and deposits belong to the team. The game page credits the team; members choose whether they're named. One payout account per team; splitting money is the team's business, since we never hold player money. Teams with 13–17 members follow the teen-safe defaults (invite links only, no private messages through Zaisma), and a teen's payout account must be parent-owned. Every team keeps at least one owner; if the last one leaves, the next publisher takes over.
- **Mods, after the beta (Phase 5).** The game developer opts in and decides what mods can change through a mod API in the SDK. Zaisma hosts and scans mods and versions them like games; the game lists and switches them on however it likes (`Zaisma.mods`), and a listing on the game's page is optional. Developers can remove mods from their game; we can take down a mod without touching the game. Mods run inside the game's sandbox. In multiplayer, everyone in a room runs the same mods, and the invite link carries them. Remixes and mods are free at first, with tips for their makers.
- **Zaisma's demo games are examples, not shelf games.** Arena and Four in a Row, the two short multiplayer demos (real-time and turn-based), are listed only until the seed games land. Then they go unlisted, still playable by link, and the developer page and docs link them as multiplayer examples to play in two tabs and read on GitHub. Player shelves hold games that stand on their own (Julius, Oct 16, 2026).
- **Tools on the developer page (Phase 4).** Free, open-source developer tools (asset pipelines, engines, level editors, Claude Code skills, MCP servers), listed on the developer page, not next to games on the home page. Browser tools upload, scan and run exactly like games, marked as a tool; others are a link to their open-source repository. Zaisma seeds it with its own (the skill, `zaisma check`, the SDK). Unparked Oct 14, 2026. Same rules as games; a tool must be open source to list.

- **Game pages say who's playing now, never how many ever played.** Games on Zaisma rooms show "151 playing now" under the title once 3 or more are in their rooms, hidden rooms included and nobody named. Play counts stay in the developer's dashboard, so new games never look empty next to big ones; ratings come with discovery (Phase 4).
- **Room browsing lives on each game's page, and in the game.** Every game on Zaisma rooms lists its open rooms on its page, so guests can jump into a match: how full each room is and where it runs (the flag and code of the country its first player connected from; rooms in the player's country, then continent, come first), never who's in it. Players can filter by region. Join is enough, so rows don't show room codes; a player with a code from a friend types it into the box above the list. Rooms can have a name and labels (like Mode: Classic), set by the game or typed by players, and players can filter by labels. Rooms show the game, labels and any name the game gives them, never the names of the players in them. Names typed by players show on zaisma.com only after Zaisma's text filter (no links, handles, emails, phone numbers or contact apps; no slurs or sexual words), and every listed room with a name can be reported; inside the game they're the developer's responsibility, with the same filter offered (`Zaisma.filterText`). The game gets the same list (`Zaisma.rooms.list`) to show its own way, and can drop players into a busy room with space (`quickJoin`). Rooms fit any kind of game, not just quick matches: the developer lists rooms on the page and in the game, only in the game (games with their own lobby or server browser), or nowhere, and a game can hide single rooms (private matches, its own matchmaking) and close a room once a match starts, while players who were in it can still come back. Join is an ordinary room link, so the game decides what happens before the player is in (a menu, a character customizer). Room codes belong to one game, so a code is entered on that game's page or arrives inside a link; there's no site-wide code box. The game page has no "Start a room" button: Play starts the game, and the game decides how rooms are made. Rooms on a developer's own servers aren't listed yet; later they can check in to the same list.
- **Updates for players, patch notes for those who dig.** Developers post updates: a title, a short text and optionally an image (checked like covers). Players see updates; version notes are patch notes, shown on the details page of the update that shipped that version, for developers and players who want detail.
- **The home page is for players.** From the top: friends (invites, who's playing and a Join button, people you played with to add), the game you played last, Continue playing (sorted by recently played or recently updated; updated games carry an "Updated" badge, never a separate card), For you (games ranked from what you play, with a full-screen daily queue of 8 picks you can refresh for more), then Games, the same lists for everyone (popular, trending, new). For you is ranked by plain rules from play data, not AI, to keep it cheap and explainable: each pick says why it's there. A first visit shows a guest note, a featured game and Games, with the queue offered after Games for players still looking. Save slots stay inside games. Developer material (publishing, the dashboard, docs) lives on a developer page, not the home page.

- **Every game can have a community, after the public beta, if its developer switches it on.** Like a Steam hub: a Community tab on the game holds the developer's updates, player posts (screenshots, clips, guides, questions) with comments, and a Mods and remixes shelf with the credit chain. The developer turns it on, picks their own moderators, and can point players to their own Discord instead; posts are theirs to read through the API. Zaisma checks posts for safety only. Profiles show the games you play, the mods and remixes you've made and your posts; teens' profiles are private to friends by default and their posts take comments only from friends, adults' are public unless they turn that off. Only accounts post. AI checks every post, comment and image before it appears (images also go through image matching), and reports go through AI triage.
- **Games manage their players; leaving a match never leaves the game.** A game server can kick a player (`room.kick`, optionally keeping them out of that room for the match) and move players to another room of the same game, new (`room.reserve`) or already running (`room.moveTo`), and the target room can say no. A closed room still takes players the game moves there (closed keeps out strangers, not the game), and holds their seats for a minute. The SDK follows a move by itself; a game that wants a loading screen first listens for it and follows when ready. A game server can also turn a player away at the door with a reason (a wrong room password, a full team), and players kicked from a lobby stay out of the match it starts. In relay games the host can kick, and when the host leaves the next player takes over. Players who walk away are handled for every game: dead connections drop after about a minute, a tab hidden for a couple of minutes in a real-time room leaves as away, and 10 minutes without input asks "Still there?" for 30 seconds (games can change or turn off the idle check). The game picks what happens next: hold the seat for a few minutes (the default), send the player to its lobby room, or handle it itself; a player who comes back is offered their old room if it has space. Zaisma never covers the game with its own screen or sends anyone to the home page for being idle. Idle and away players don't count as playing now or toward how full a room looks.
- **Games can find their players across rooms, never anyone else's.** Each game can ask which of its rooms its players are in and message another of its rooms, for in-game friends lists, parties and join a friend. Only from the game server, only within that game; blocks always apply, players can appear offline, and teens can be found only by friends by default. Developers' own servers do this themselves with the same player passes.
- **Games decide who plays; Zaisma proves who's who.** Developers choose guests, accounts only or a mix, for a room, for multiplayer or for the whole game; a game can ask the player to sign in whenever it likes, and the game page says "Needs a Zaisma account" before Play when the whole game does. Guests are the default: a game takes everyone unless it asks for accounts, and a signed-in player plays as their account in every game while everyone else plays as a guest (Julius, Oct 16, 2026). Zaisma's part stays small: the player pass is proof of who the player is (the ID, guest or account, the game and when it expires; guests also get their generated name) and nothing more, so any server can check it without asking us. Everything else a game learns, it looks up. For the whole game or multiplayer it's one game setting (`account_requirement`), and the backstop is the pass: guests of such a game get no passes, and Zaisma rooms turn away guest passes made before the change; the page's sign-in prompt is only so honest players never start a game that turns them away (Oct 16, 2026).
  - *Signing in from a game:* any game asks whenever it likes with `Zaisma.player.signIn()`. The ask is Zaisma's, beside the game rather than in it: a card on the game page, in the "Keep your progress" card's place, names the game and offers an account, a sign-in and Not now, and signing in happens in a new tab so the game keeps running. A game can't fake the card or see the account's details; it hears only the player's ID, name and kind once they've signed in, or `sign_in_declined`. However the player signs in mid-game (this card, "Keep your progress" or another tab), the page tells the game, and in a game with player passes trades the guest's room key for one to the account's: the guest's key is the proof that Cloudflare checked the browser, used once, and the account's runs out when the guest's would have. Rooms the player is already in keep them as the guest they joined as (Oct 16, 2026).
- **A Zaisma account works in every game.** One ID everywhere, so a developer can recognize a player across their games and their own sites. Any game, developer server or anyone else can look up a player's public profile by ID and gets exactly what a stranger sees on the profile page (name, username, profile, games played, activity and stats, as each exists), read-only. Never shared: email, age, purchases in other games, other games' saves, block lists, location, or anything the player didn't make public. Teens' profiles are private to friends by default, so games see little more than a teen's name, and only friends see where a teen is playing. Phase 2's owned items are the one planned addition to the pass.
- **Bans, moderators and roles belong to the developer.** Games keep their own lists by player ID, on their own servers or in their game's database on Zaisma. Zaisma keeps only what's safety: its own account bans, mute, block and report, the content rules and teen privacy.
- **Every game gets a real database with its hosting.** Tables and queries, used straight from its game servers, with full access for the developer and their AI: query, change tables, fix data, import and export. No Zaisma forms or key-and-value screens. On the developer's own server the same calls use a local database file, so moving off Zaisma takes the data along. What's in it is the developer's, under the content rules. Free up to a limit per game, then priced with a margin like rooms, from the same prepaid credit.
  - *How it works:* one SQLite database per game in a Durable Object of its own, shared by all the game's rooms; game servers use it as `room.database` (`query(sql, values)` and `batch(statements)`, one transaction). A sandboxed game server gets it as its only binding, fixed to its own game. The Node runner uses a local SQLite file with the same calls, checked by the same code (one statement per query, no transaction statements, text, numbers, null and blobs as values), so a query that works in one works in the other.
  - *The developer and their AI:* the developer API, MCP (`get_database`, `query_database`, `batch_database`) and `zaisma database` reach the same live database through a service binding from the site to the rooms Worker, with the same checks, limits and counted use as game servers, plus what each statement read and wrote. Blobs travel as `{ blob_base64 }`; answers stop at 8 MB. The overview shows tables, indexes and the month's use against the free limits, and keeps working past them; it gives no row counts, since counting reads every row (Oct 16, 2026).
  - *Import, export and undo:* the whole database goes out and comes back in as SQLite's own SQL dump (`CREATE TABLE`s and `INSERT`s), through the API, MCP and `zaisma database export` and `import`, about 4 MB at a time; the CLI also writes and reads a ready `.sqlite` file, the same one the Node runner uses, so moving between Zaisma and the developer's own server is one command each way. Export works past the free reads (its reads still count): the data is always the developer's to take. Import only adds, counts its writes like any write and stops at the free writes; each chunk is all or nothing, the whole import isn't. Export reads table by table, so it isn't a snapshot while the game is writing. The database can be restored to any minute in the last 30 days (Cloudflare keeps that history at no cost), and a restore can itself be undone: the undo for a bad import, a game server bug or an AI's wrong `DELETE`. It's for the developer and their AI, never players. The dashboard's database page is a console like Cloudflare D1's: tables with their SQL, rows to browse, a SQL box, export, import, restore and the month's use. Changes go through SQL; no cell editing or forms (Julius, Oct 16, 2026).
  - *Free use and prices:* per game, 500,000 rows written and 500 million rows read a month (UTC) and 500 MB stored, about $1.10 a month at Cloudflare's prices if all used. Until Hosting billing, a game past its written rows can't write until the month resets, and one at its storage can change and delete rows but not grow; reads keep working. Past its read rows, it waits for the month too. Above the free use, about twice Cloudflare's price: $2 per million rows written, $0.002 per million read, $0.40 per GB-month (Julius, Oct 16, 2026).
- **Developers' AI files bugs and feature requests straight to us.** Feedback about Zaisma itself (bugs, gaps, feature requests, questions) comes in through the developer MCP (`post_topic`, `message_zaisma`), the API, the upload command (`zaisma forum`) and the dashboard, and the MCP asks AIs to file whenever they hit a bug or a limit. Each item is a thread: the developer and their AI can add context and screenshots to their own items and reopen fixed ones. Known issues (merged and cleaned up by Zaisma: title, status, workaround, roadmap item, how many developers it affects) are open to every developer and their AI, so an AI checks them before filing and adds its own case to one instead of filing a duplicate. Each new item gets known matching issues and workarounds at once; AI merges duplicates and sorts by severity (developers pick the category), then Julius decides in the admin MCP or dashboard and links them to the roadmap. Developers see where each one stands and hear when it's fixed. Every post says whether the developer wrote it or their AI did: posts through the MCP are always marked AI, posts from the dashboard are the developer's own, and the API and upload command say which (AI unless told otherwise). Private reports are messages to Zaisma, and all of it lives in the developer forum (below); Julius can copy a cleaned-up version to public GitHub issues. Secrets in the text are blanked before storing, and each account can post about 100 times a day (new items, additions and reopens alike) (Oct 14, 2026).
- **The developer forum, built now as Zaisma's own community.** Feedback lives in a forum at zaisma.com/forum, built on the game communities building block ahead of the public beta, so every game later gets the same thing. Ideas, questions and discussions are public topics every developer and their AI can read, reply to and vote on ("Affects me too" on bugs and known issues, "I want this" on ideas, "Same question" on questions; discussions take replies). Whoever posts picks the category; when someone flags a topic as misplaced, Zaisma's AI moves it and says so in the topic, and AI never sorts categories otherwise. Every topic is public. Anything private (logs, unreleased games, a developer's own case) is a message to Zaisma, a private conversation inside the forum that only the developer and Zaisma see; developers never message each other. When Zaisma confirms a problem others hit too, it becomes a public known issue of Zaisma's own, pinned in its category, and the private reports count under it. Topics sit in categories with sub-categories (publishing, multiplayer, building games, MCP and API, accounts, safety, general) and a fixed set of tags. Every post shows the account's name and picture; an AI's post shows its developer with an AI mark, and Zaisma's posts show Zaisma's. Replies can answer one post or the whole topic, and the asker or Zaisma marks the answer. Any reply can be marked Helpful (no dislikes: a wrong reply gets a better one, a harmful one a report), and any post can be reported: a child-safety report or three reports from different developers hide it until a person looks. Posts are markdown, written with a toolbar (Insert for images, links, videos and code; formatting in the bar and over a selection) and a preview, with code blocks (Copy and Wrap), up to ten images placed in the text, and @mentions that reach the person (the name is saved to the account when it's posted). Links to Zaisma open directly; links elsewhere first say where they go, and a viewer can trust a site in their browser; YouTube, Vimeo and Streamable links play in the post. Every forum image is matched against known abuse material as it is uploaded (a match takes down only that image and alerts Julius), and AI checks every public post, its images included, before others see it; images in a message to Zaisma, and anything an AI attaches, stay private to the developer and Zaisma. Anyone with an account can post and reply, teens included, with no private messages, and no age is shown or filterable. Known issues move through phases everyone sees: investigating, confirmed, planned, fixing, fix released (Zaisma watches that it holds, and a developer saying it still happens takes it back to fixing) and resolved, or won't fix. Everything is in the API and MCP, so an AI searches the forum instead of scraping a site: ranked full-text search, with brief results and topics readable in part to keep an AI's reading short (Oct 14, 2026).
- **Achievements, like Steam's.** The developer defines a game's achievements (name, description, icon checked like covers); the game or its game server unlocks them (`Zaisma.achievements`, signed from the game server when it matters). They show on the player's profile and the game page, and the developer reads and manages them through the API. Zaisma never invents badges for a game; Zaisma's own badges (like Scout) stay separate (Oct 14, 2026).
- **Game servers are full building blocks.** Besides rooms, a game's server code can answer plain requests (an endpoint per game, for leaderboards or a shop in a single-player game) and run on a schedule (daily resets, persistent worlds), reach the developer's own listed servers, and keep secrets set per game. The same code runs on the developer's own server (Oct 14, 2026).
  - *Requests, how they work:* the game server's `onRequest(player, request, server)` answers `Zaisma.server.request(request)` with plain JSON, outside any room, with `server.database` its game's database. The game sends `{ pass, request }` to `POST /v1/requests/<slug>`, on rooms.zaisma.com or the developer's own server (the Node runner answers it on its port), so the server always knows who's asking from the player's pass. Requests come from the live version's game server whatever the multiplayer setting, and a game server with only `onRequest` needs no `setup()` and runs no rooms. On Zaisma one object per game keeps the sandbox open and counts requests, so each costs one call into the sandbox. Limits: 16 KB a request, 1 MB an answer, 10 seconds, about 120 a minute per address, and a game server that keeps running on too long is paused for a few minutes (Oct 16, 2026).
  - *Free use and prices:* 1 million requests a month per game, at most about $0.80 at Cloudflare's prices. Until Hosting billing, past them requests answer `request_limit` until the month resets (UTC); above them, priced with a margin like rooms, from the same prepaid credit (Julius, Oct 16, 2026).
  - *Schedules, how they work:* the game server lists `schedules`, up to 10 `{ name, cron }`, with standard five-field crons always in UTC (so at most once a minute; faster belongs in a room's `onTick`), and `onSchedule(run, server)` runs at each with `run.name`, `run.cron`, `run.scheduledAt` and `server.database`, for up to 30 seconds. They're checked like any option, and a cron that doesn't read stops the game server starting. On Zaisma the game's object (the same one that answers requests) keeps one alarm for its next due run; the rooms Worker's cron, every minute, asks it to read the schedules again when the live version isn't the one it read, so they start within a minute of a publish, and before each run it checks the version is still live and players can play the game, so a new version or a takedown stops the old schedules. A run is at least once, rarely late or twice, so a run should be safe to repeat. The Node runner runs the same crons with timers while it's up and misses runs while it's down. Stats show each schedule's next and last run, runs per day and errors named by schedule (Oct 16, 2026).
  - *Schedules are free, capped by their shape:* 10 schedules at most once a minute is at most 432,000 runs a month per game, about $0.40 at Cloudflare's prices, so there's no monthly count and no limit error. They get priced with Hosting billing only if they're abused (Julius, Oct 16, 2026).
- **Developers hold the keys.** API keys can be limited to some of a developer's games and to what they may do, for CI and collaborators: one of four fixed levels (read, upload, publish, full, the same words as the Teams roles) or, for advanced use, a custom choice per area that the levels are shortcuts for. Read and upload keys can read the forum but can't post or message Zaisma in the developer's name. Keys are still made only on the account page (Oct 16, 2026). Webhooks send every event (bug reports, scans, publishes, purchases, room events, deleted accounts) to an address the developer sets, signed, and are how follower alerts, Discord posts and purchase notifications reach developers. One command exports everything about a game: files, versions, database, saves, stats, reports and updates (Oct 14, 2026).
- **Webhooks follow Standard Webhooks.** A developer sets up to 10 webhooks through the API and MCP, each an https address, the events it takes and optionally which games. Events are signed the way Standard Webhooks (standardwebhooks.com) says (`webhook-id`, `webhook-timestamp`, `webhook-signature`, a `whsec_` secret answered once), so its libraries check them in any language, and each carries the same objects the API answers (`game`, `version`, `bug_report`). The first events are bug reports, scans, which version players get, and holds and takedowns; room events, deleted accounts and purchases join later. Each event is tried straight away, then after 5 minutes, 30 minutes, 2, 8 and 24 hours; what was sent and how it went is kept 30 days, readable through the API. The signing secret has to be kept as it is to sign with, so it's stored in the database, never listed again. Addresses are https names, never IP addresses or Zaisma's own domains, and redirects aren't followed. Webhooks carry no Zaisma formats for other services (a GitHub issue, a Discord post): the developer's own small server turns events into those, with their own tokens (Oct 16, 2026).
  - *Webhooks to the game server:* developers with no server of their own get Discord posts and GitHub issues too, because a webhook can point at the game's own game server on Zaisma instead of an https address. Its code turns events into whatever it likes with the developer's own tokens (kept as the game's secrets) and calls Discord, GitHub or anything else it lists through game server reach; Zaisma still makes no formats for other services (Julius, Oct 16, 2026). How: such a webhook takes only that game's events, which reach the live version's `onWebhook(event, server)` with the same JSON a signed delivery carries and `server.database`, with the same retries, delivery list and test event; an answer without an error counts as delivered. Each delivery counts as one of the game's requests. On the developer's own server the Node runner takes the signed POST at `/v1/webhooks`, checks it with the webhook's `whsec_` secret and calls the same `onWebhook`, so the code moves unchanged.
- **Sign in with Zaisma ships with Zaisma accounts in games.** One OAuth server serves developers' own sites and servers, games with their own accounts, and the MCP sign-in without a key (Oct 14, 2026). It's standard OpenID Connect on zaisma.com, so any library works: developers make sign-in apps through the API and MCP, and a site gets what a game gets, the player ID (the same everywhere) and the public name, never the email. Players say yes once per app on a Zaisma page that names the developer and the address they go back to, and can remove an app from their account at any time. Tokens are signed with RS256, the algorithm every library takes, by a key of the site's own, separate from the player pass key (Oct 16, 2026).
- **Saves and the database have separate jobs.** Cloud saves are the player's own progress, mirrored from the browser: free, no code, never paywalled. The game database holds what the game server owns, shares or must trust (inventories, leaderboards, bans, worlds), priced past its free limit. Saves never move into the database (Oct 14, 2026).
- **Developers get their game's saves.** Through the API and MCP they list which players have a save, read a save by player ID (whole or some keys), change it (some localStorage keys or the whole save), reset it, and read and restore its earlier versions; "export everything" includes them. A developer's change keeps a copy of the save it replaces first, unless that save was the developer's own last change, and those copies are kept like progress about to be lost, so a script can't push the player's own copies out. A change reaches a game that's open by reloading it with the new save, with no dialog; that device's progress is kept as an earlier version. Saves stay tied to the player: deleted with the account, never shown to other games (Oct 14, 2026; Julius, Oct 16, 2026).
- **Zaisma hosts saves; the game owns their rules.** Zaisma's part is the plumbing: mirroring the game's browser save to the account, the backstop copies and full access for the developer. What progress means is the game's: whether a player can go back, which progress wins, slots and resets. So Zaisma draws no save screens over games and players get no save manager: no conflict chooser, no restoring from the account page or the game menu, no list of a game's copies. A game that wants any of it builds it with the SDK (`Zaisma.saves.onConflict`, `getHistory()`, `restore()`), and offers an account when it likes (`Zaisma.player.offerAccount()`) (Julius, Oct 16, 2026).
- **Deleting an account reaches developers.** An "account deleted" webhook tells every game the player used, and the developer erases that player's data on their side; their game database on Zaisma has a one-call helper for it (Oct 14, 2026).

## Brand

- **Logo: Julius's metal Z** (based on Futura) plus custom shard letters "aisma", lowercase z. Files and usage rules in [`brand/`](../brand/README.md).
- **Metal only on dark.** One-color black/white elsewhere; a small-size Z for 32 px and below; tri-color for special editions.
- **Zaisma is where you play games, not the game.** Like Steam, not Roblox: nobody plays Steam, they use it to play games, so a game's name, art and reputation are its own. The product says so everywhere: game cards are the developer's cover alone, with their name and logo in their own art and nothing of ours over it; the game page credits the developer; and copy says "play Shard Dodge on Zaisma", never "play Zaisma". Only a Play button starts a game; a card or Details opens the game's page first, so nobody loads a big game by accident. We still host, check and moderate every game, as a store does.
- **They're game developers, not creators.** "Creator" is overused and corporate. In copy, docs and the product we say game developers (or developers, devs), and players.
- **Steel is the look.** Today's dark greys with the metal wordmark. Highlights take the Z's metal: white and black edge lines on the bevel, and a glint that only moves on hover. The element tilts toward the cursor, less the bigger it is, and the glint is the reflection of a fixed light sliding across the tilted surface rather than a spot under the cursor. Metal buttons' labels are stamped in and take no light; a game card is the developer's cover alone, and reflects like glass. The hover area never tilts, so edges can't flicker. No tilt when the player asks for reduced motion. Nothing animates on its own.
